# Build Prompt: Single-File Node.js Server Management Portal

Build me a **single `server.js` file** that runs on a fresh Ubuntu install with nothing but Node.js installed. It should be a complete, production-feeling server management portal. Everything below is a firm requirement unless marked optional.

---

## 1. Hard constraints

- **Zero npm dependencies.** Pure Node.js standard library only. Node 18+, assume Node 20/22.
- **No CDN, no external assets.** No web fonts, no JS libraries, no icon packs. The portal must work fully offline on a machine with no outbound internet. This means:
  - TOTP implemented with `crypto` (HMAC-SHA1)
  - QR code generation hand-rolled in pure JS (byte mode, ECC level M, auto mask selection) so the authenticator secret can be scanned rather than typed
  - Syntax highlighting hand-rolled
  - Charts/sparklines as inline SVG
  - System font stacks only (`ui-sans-serif`/`-apple-system`/`Segoe UI` and `ui-monospace`/`SFMono-Regular`/`Menlo`/`Consolas`)
- **Everything in one file.** The entire HTML/CSS/client-JS for the portal lives as a string inside `server.js`.
- On first run it creates a **`Server/`** folder alongside `server.js`. All server data besides `server.js` itself lives in there, organised into logical subfolders.
- **Default port 8080**, bound to `0.0.0.0`. This leaves 80/443 free for Caddy and avoids needing root. Port configurable in settings.

---

## 2. Process model, self-update and rollback

Three process roles in the one file:

- **No flag** → supervisor: forks and watches the worker
- **`--child`** → worker: the actual HTTP server
- **`--probe --port=N`** → probe mode: boot end-to-end, confirm health, print `PROBE_OK`, exit

Use **systemd if available, self-fork supervision as fallback**. Provide a button that generates and installs a systemd unit (`Restart=always`).

Exit codes: `88` = clean restart requested, `89` = restart into replaced `server.js`.

**The self-update flow must be:**

1. Live syntax check in the browser before the Update button is even enabled
2. Server-side `node --check` on the candidate
3. **Probe boot**: spawn the candidate on a spare port and require it to answer a health check — this exercises the full supervisor→worker boot path, so a broken supervisor section is caught too
4. Only then back up the current `server.js` into `Server/backups/server.js/` with a timestamp
5. Promote the candidate, write a `update-pending` marker, exit 89 to restart
6. If the new file fails to become healthy, the supervisor **automatically restores the most recent backup** and surfaces **the exact stderr** so it is obvious what went wrong
7. Crash-loop detection (3 failures in 60s) also triggers rollback
8. Keep the 20 most recent `server.js` backups

Nothing is overwritten until the probe boot passes. A failed update must leave the running server completely untouched.

## 3. Authentication

- **Single admin account only.** No roles, no multi-user.
- First visit to `/admin` shows account creation: **Username + Password + TOTP**. Show the QR code (scannable) *and* the secret as text.
- After creation or sign-in, go straight to the dashboard.
- **Login protections required:**
  - Rate limiting with progressive temporary lockout per IP (5 free attempts, escalating, capped ~15 min)
  - **One-time recovery codes** — 10 generated at setup, displayed once, stored hashed (SHA-256). Consuming one removes it and raises a warning.
  - Auto-logout after configurable inactivity (default 120 min)
- Deliberately **no first-run setup token** — the setup page is open. To compensate, log the claiming IP, user agent and timestamp, and fire a notification when the portal is claimed.
- Session cookie: `HttpOnly`, `SameSite=Lax`, scoped to `/admin`. Sessions persist across restarts. Session list with revoke.
- Password hashing with `scrypt` + per-record salt, constant-time comparison.

## 4. Static hosting — GitHub Pages semantics exactly

`Server/public/` is served from the site root. Behaviour must match GitHub Pages precisely:

| Request | Result |
|---|---|
| `/` | `public/index.html` |
| `/test.txt` | `public/test.txt` |
| `/testfolder/test.txt` | `public/testfolder/test.txt` |
| `/docs/` | `public/docs/index.html` |
| `/docs` (a real directory with an index) | **301 redirect** to `/docs/` |
| `/about` | falls back to `public/about.html` (clean URLs) |
| anything missing | `public/404.html` served **with a real 404 status**, else plain 404 |
| dotfiles | hidden, never served |

- **No directory listings.** A folder without `index.html` is a 404.
- **No SPA catch-all.**
- Support ETag/`If-None-Match`, `Last-Modified`, and HTTP Range requests so media seeks properly.
- Seed a starter `index.html` and `404.html` on first run.

**Routing priority:** `/admin` → `/share/:id` → custom API endpoints → public folder.

## 5. Portal tabs

### 5.1 Dashboard

Full server health. Read from `/proc` and `/sys` directly rather than shelling out, for speed.

- Hardware breakdown: hostname, distro, kernel, arch, CPU model/cores/speed, total RAM, vendor/board, Node version, boot time
- Live CPU (total + per-core), RAM (used/available/cached/swap)
- **Disk usage per mount + disk I/O rates**
- **Network throughput per interface + public IP**
- **Load average, uptime, temperatures, top processes**
- **Pending apt updates + `reboot-required` flag** (cached, apt simulation is slow)
- Running Docker containers with health status and per-container stats
- Easy system update from here

**Metrics history:** live values streamed over **SSE**, plus history rolled into **60-second buckets persisted to disk, 24h retention**, in a compact ring so it can't grow unbounded. Render as inline SVG charts.

### 5.2 File manager

Full-blown, interactive, professional. **Jailed to the `Server/` folder** — no browsing the wider filesystem.

- Browse folders, breadcrumbs
- Open, edit and save any text file
- **Drag-and-drop upload** (preserving dropped folder structure) and **download a folder as a zip** (implement the zip writer with `zlib.deflateRaw` + CRC32)
- Create files and folders, delete, **rename / move / copy / chmod, with a permissions view** (mode, owner)
- Built-in editor with **syntax highlighting**, including **HTML**, plus CSS, JS, JSON, YAML, shell, Markdown, INI/env and Caddyfile
- **Tab inserts 4 spaces**, and indents/outdents correctly across multi-line selections (Shift+Tab to outdent)

### 5.3 server.js editor

- Shows the entire current `server.js` in a large code-editor-styled textarea with syntax highlighting and line numbers
- **Live syntax check — the Update button stays disabled until the code parses**
- Update → backup → probe → promote → restart, per section 2
- Show the backup list and the outcome of the last update attempt, including the failure reason if one occurred

### 5.4 Docker

- **One-click Docker install** with live streaming output
- Edit `docker-compose.yml` directly in the portal
- **Pre-made one-click apps: Caddy, n8n, MeshCentral** — designed so that enabling all three and starting them Just Works together. Structure the catalog as a definition list so a fourth app is a small edit, not surgery.
- Per-container controls:
  - Start / stop / restart / remove
  - **Live streaming log viewer**
  - **Interactive exec shell into the container**
  - **Per-container CPU / RAM / network stats**
  - **Pull latest image and recreate** — per container *and* for the whole stack
- Compose actions: up, down, restart, pull, pull-and-up, stop
- Image list and prune

**Caddy specifics:**
- The `Caddyfile` must be easy to edit from the portal, with a reset-to-default and a `caddy reload` button
- The generated default `Caddyfile` contains **three commented example domain blocks**:
  1. Apex domain → the Node server (so `/admin` *and* the public folder both work over HTTPS; the admin portal remains reachable only at `/admin`, everything else on that domain comes from the public folder)
  2. `n8n.example.com` → the n8n container
  3. `mesh.example.com` → the MeshCentral container
- Include `host.docker.internal:host-gateway` mapping so the Caddy container can reach the Node process on the host

**n8n specifics:**
- Data stored in the `Server/` folder with everything else (`Server/docker/n8n/data`)
- **Fix the permissions** — n8n runs as uid/gid 1000 inside the image, so `chown -R 1000:1000` the bind mount and run the service as `1000:1000`. Expose a "fix permissions" button too.

**No secrets manager** — but still generate and manage a plain `.env` from the Docker tab holding `TZ`, `N8N_HOST`, `MESH_HOST` and a generated `N8N_ENCRYPTION_KEY`.

### 5.5 API endpoints

- "New endpoint" button creates a **unique string route** which **takes priority over the public folder**
- A code textarea per endpoint for a JS function that runs on every request to it
- **Method toggles** — GET, POST, PUT, PATCH, DELETE, ALL
- **Names for endpoints, and search** across name and route
- Handlers get **full access to the server internals**: `require`, the settings, the helper library, plus `req`/`res`
- Convenient body access: `body` **pre-parsed** for JSON, form-encoded, multipart and raw text; also `rawBody`, `query`, `params` (`:param` route segments), `headers`, `method`, `ip`
- Response helpers: return a value for automatic JSON, or `json()`, `text()`, `html()`, `send()`, `status()`, `header()`, `redirect()`
- **Cron schedule trigger** in addition to HTTP (standard 5-field cron with `*`, `,`, `-`, `/` and `@daily`-style aliases)
- **Execution log with a last request/response inspector** per endpoint — timestamp, trigger, method, IP, status, duration, captured `log()` output, errors
- **Containment: try/catch plus a per-endpoint timeout returning 504**, with the error captured into that endpoint's execution log and a notification raised on timeout
- Manual "run now" test button

**`data.json`:** a general-purpose store at `Server/data/data.json`, editable from the portal, with helper functions available inside every API handler — `db.get()`, `db.set()`, `db.del()`, `db.push()`, `db.incr()`, `db.keys()`, `db.all()`. Dot-path keys. **Atomic writes** (temp file + rename) so a crash mid-write can't corrupt it.

*(Not wanted: per-endpoint secret tokens, per-API isolated key/value stores.)*

### 5.6 Web terminal

- A shell tab that runs commands as the server user with live streamed output
- Persistent session so `cd` sticks
- No allow-list — full access
- Acknowledge in the UI that this is a command runner, not a true PTY: `apt`, `docker`, `git` and scripts work; `nano` and `top` will not
- Reuse the same mechanism for the container exec shell

### 5.7 Backup and restore

All four of these:

- **Full archive** — `server.js` + the entire `Server/` folder
- **Config-only** — settings, auth, APIs, `data.json`, compose, `.env`, Caddyfile, apps state
- **Scheduled automatic backups with a retention limit**
- **Restore preview** showing exactly what will be overwritten, what is identical and what is new, before anything is applied

Implement a minimal **tar + gzip writer and reader** with `zlib` — no external tooling needed to create *or* restore. Include a manifest in the archive. Guard against archive path traversal. Back up the current `server.js` before a restore overwrites it. Reload in-memory state after a restore.

### 5.8 Maintenance

- **apt update / upgrade / full-upgrade / autoremove / clean, plus host reboot**
- **Docker prune** — images, volumes, build cache, containers, or everything
- **Log viewer** — portal event log, access log, and the systemd journal
- **Disk usage explorer** — largest files and folders, drill-down, bounded scan
- Install-as-systemd-service button

### 5.9 Settings

- Site name, port, host, session idle timeout, metrics interval and retention, API timeout, max upload size
- Domains used to generate the Caddyfile
- Alert thresholds and webhook URL
- Change password, regenerate recovery codes, view/revoke sessions
- Theme toggle

## 6. Alerts and notifications

**In-portal notification bell plus an outbound webhook.**

- Threshold rules: sustained CPU above X% for N minutes, memory above X%, any disk above X%, container exiting or disappearing
- **Every sign-in raises a notification** with IP, user agent and timestamp, so sign-ins are easy to track
- **Failed sign-in attempts too**, with attempt count and IP
- Also notify on: portal claimed, password changed, recovery code used, server.js updated, scheduled backup created or failed, endpoint timed out, host reboot requested
- Webhook payload should include a plain `text`/`content` field so chat webhooks render it as-is without extra mapping
- Levels: info / warning / critical

*(Not wanted: a separate scheduled-tasks manager — the API cron triggers cover it. Not wanted: a secrets manager.)*

## 7. Temporary share links

From the file manager, generate a one-off public URL like `/share/a7f3c9e2` for any single file — **with an optional expiry and a download limit** — without moving the file into `public/`. List active links with their status (active / expired / exhausted) and allow revoking. Count downloads. Expired entries linger a day so the UI can explain what happened.

## 9. Visual design

**Dark by default with a light-mode toggle**, driven by CSS custom properties so the switch is instant and persists per browser.

Aesthetic direction: an **instrument panel**. Cool ink-navy base, **tabular monospace numerals for every piece of live data**, one signal-blue accent, and semantic ok / warning / critical colours used consistently. Avoid the generic dashboard look — no gradient hero cards.

**Signature element:** a persistent **vitals rail** in the top bar, live on every tab, showing CPU / memory / disk / network with tiny inline sparklines.

Also required:
- Responsive down to mobile (collapsible sidebar)
- Visible keyboard focus states
- `prefers-reduced-motion` respected
- Copy written in plain language: say what a control does, name things by what the user recognises, and make empty states and errors actionable rather than vague
